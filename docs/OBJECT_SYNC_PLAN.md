# Синхронизация с per-object разрешениями

Статус: требования и план следующего этапа, **не реализовано**. Текущий
`ModelSyncEndpoints` протокола 2 предоставляет доступ ко всей модели и не
применяет `get_queryset()` к журналу. Этот документ уточняет новый контракт;
существующие клиенты, БД и ожидающие запросы пока работают по прежнему протоколу.

## Требуемое поведение

Объект имеет один UUID, одну серверную запись и общую ревизию. Его одновременно
могут читать или изменять несколько пользователей через per-object разрешения,
в том числе полученные через группы и связанные объекты. Область по владельцу
или копирование объекта в отдельную область каждого пользователя не подходят.

CRUD и sync должны использовать один источник правил доступа. `get_queryset()`
может определять доступную выборку, но произвольного фильтра недостаточно для
отслеживания изменений доступа. Серверу также нужны сведения об изменениях ACL,
членства в группах и связей, влияющих на разрешения. Пользователь определяется
из доверенной авторизации, а не из тела запроса или выбранной клиентом области.

| Изменение | Что получает пользователь | Действие клиента |
| --- | --- | --- |
| Появилось право чтения | Полное разрешённое текущее состояние | Добавить объект в локальную проекцию |
| Изменился доступный объект | Разрешённое изменение или каноническое состояние | Обновить проекцию с учётом локальных правок |
| Отозвано право чтения | Событие отзыва без содержимого объекта | Убрать объект из доступной проекции |
| Объект удалён на сервере | Событие удаления для соответствующих получателей | Применить серверное удаление |
| Отозвано только право изменения | Актуальный результат проверки прав | Сохранить чтение, запретить новые записи |

Отзыв доступа не является удалением объекта: другие пользователи продолжают
работать с той же записью. Изменения прав должны попадать в доставку, даже если
бизнес-поля объекта не изменились. При выдаче доступа не следует отправлять
исторические diff с данными, которые пользователь ранее не имел права видеть.

## Журнал данных и доставка

- Общий журнал модели продолжает описывать изменения авторитетных данных.
- Отдельная лента доставки отражает доступные конкретному пользователю объекты,
  выдачу текущего состояния и отзыв. Конкретная физическая схема ленты ещё
  требует реализации; это не существующий API протокола 2.
- Идентичность ленты и курсор привязаны к серверной истории, аутентифицированному
  пользователю и модели. Чужой курсор нельзя использовать для чтения другой ленты.
- Запись данных/ACL и фиксация работы по доставке должны быть атомарными.
  Если раскрытие групповых разрешений выполняется фоново, нужна долговечная
  очередь и определённый порядок; курсор не может перескочить незавершённую работу.
- Смена ACL во время пагинации, повторы страниц и перезапуски не должны терять
  grant/revoke или приводить к повторной выдаче уже недоступного содержимого.
  Сохранённая лента не заменяет актуальную проверку разрешений перед раскрытием.
- Новая выдача доступа передаёт полное текущее состояние: нельзя предполагать,
  что у клиента уже есть предыдущие ревизии объекта.

Недостаточно добавить `WHERE` к текущему модельному журналу. Отсутствие объекта
в отфильтрованной странице не сообщает клиенту, был ли доступ отозван. Фильтр
по текущим данным также не описывает предыдущую видимость удалённой записи.

## Запись, повтор и офлайн-правки

Права изменения проверяются на сервере для каждой операции, включая отложенную
офлайн-запись. Клиентское знание прав не является разрешением на серверную запись.
Повторы сохраняют прежние operation/replica IDs, тело и базовую ревизию; ACL
не должен разрушать идемпотентность или менять уже зафиксированный результат.

При этом повтор старой операции после отзыва чтения не должен раскрывать
канонический объект из сохранённого receipt. Новый контракт должен различать
подтверждение исхода собственной операции и право получить её содержимое:
предусмотреть безопасное подтверждение без данных, не переписывая receipt.
Неизвестный исход отправленного запроса нельзя молча считать отклонением.

Отзыв чтения убирает объект из активной локальной проекции, но не должен молча
терять пользовательские правки или переписывать отправленные запросы. Нужны
явное состояние «доступ отозван», прекращение новых отправок и согласованная
политика удержания/удаления локальных данных. Не следует автоматически
восстанавливать отозванный объект на сервере из локальной копии.

Пользователь без сети узнает об отзыве только после связи с сервером. Протокол
не может гарантировать немедленное удаление ранее скачанного содержимого с
отключённого устройства; серверный запрет чтения/записи действует независимо.

## Связи и вложенные данные

Разрешение на объект не даёт автоматически разрешения на его FK-родителей,
дочерние объекты или вложенный сериализатор. Нельзя отправлять недоступного
родителя только для удовлетворения локального FK. До реализации нужно определить
правила доступности связей и локальной проекции: допустимые схемы, скрытые
ссылки либо явно ограниченные представления. Проверки прав выполняются до
раскрытия вложенных данных; сериализаторы по-прежнему не запрашивают БД.

## Границы слоёв

| Слой | Ответственность |
| --- | --- |
| Приложение | ACL, группы, зависимости разрешений и политика локальных данных |
| che-rest | Доверенный principal, общий REST/sync контроль доступа, HTTP-контракт |
| che-sync-protocol | Нейтральные события выдачи/изменения/отзыва и идентичность ленты |
| che-sync | Транзакционная доставка, курсоры, receipts и клиентское применение событий |
| che-orm | Запросы, транзакции, схемы и compiled migrations без HTTP/ACL приложения |
| che-tauri | Invoke, состояние доступа в UI, явное разрешение офлайн-конфликтов |

## Последовательность реализации

1. Определить версию и согласование нового протокола, события доступа, курсоры,
   безопасные подтверждения операций и политику локальных правок после отзыва.
2. Определить общий источник CRUD/sync разрешений и способ атомарной фиксации
   изменений ACL/групп/связей. Не выдавать новый механизм за автоматическую
   поддержку произвольного `get_queryset()`.
3. Добавить compiled follow-up migrations для доставки и состояния доступа.
   Сохранить UUID, ревизии, историю, receipts и ожидающие операции.
4. Реализовать согласованную первичную выдачу, гранты, изменения и отзыв с
   безопасной пагинацией, повтором и обработкой фоновой очереди.
5. Подключить HTTP-эндпоинты и проверку операций, сохранив обычные CRUD-маршруты.
   Существующий whole-model режим не должен незаметно менять семантику.
6. Реализовать клиентское применение, смену доступной проекции и явное состояние
   неотправленных/отправленных правок после потери разрешений.
7. Расширить Todo-пример совместным доступом двух пользователей и UI отзыва.
8. Проверить оба backend, HTTP, Tauri и явную миграцию существующих клиентов.

## Обязательные сценарии проверки

- Один UUID доступен A и B, недоступен C; отзыв у A не меняет данные B.
- Выдача доступа к давно существующему объекту передаёт полное состояние без
  запрещённой истории. Повторная выдача после отзыва корректна.
- Отзыв/выдача через группу или связь доставляется без изменения полей объекта.
- Нет утечки через старую страницу, чужой курсор, вложенный сериализатор или
  повтор receipt после изменения ACL.
- Данные, ACL и события доставки не расходятся при rollback, crash и повторе
  фоновой задачи; пагинация не пропускает изменения доступа.
- Правки разных пользователей сливаются по общим ревизиям одного объекта;
  пересекающиеся изменения остаются обычными конфликтами.
- Отзыв чтения/изменения во время офлайн-работы и потерянного ответа не теряет
  неизвестный исход отправки и не раскрывает запрещённое содержимое.
- Удаление объекта и отзыв доступа применяются как разные события, включая
  недоступные связанные строки и отложенную FK-проекцию.
- Старые whole-model и scoped клиенты сохраняют контракт, пока приложение явно
  не выполнило поддерживаемый переход; автоматического сброса outbox нет.
